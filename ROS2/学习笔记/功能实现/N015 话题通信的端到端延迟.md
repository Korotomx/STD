# 话题通信的端到端延迟 · 功能实现 · N015

**时间:** 2026-10-05 13:28
**标签:** #功能实现 #Topic话题 #QoS #延迟Latency #DDS #Executor执行器
**关联:** [[N002 QoS队列深度10]] [[N009 Executor事件循环]] [[N010 订阅者与回调参数]] [[N011 ROS2分层架构]]

## 疑惑点

publisher 和 listener 肉眼看起来是「同步」传输的，但实际是不是有延迟？量级多少、受什么因素影响、工程上会有什么问题？

## 实际情况

1. **确实有延迟，只是太小、肉眼看不出**。端到端延迟 = 从 `publish()` 到订阅回调执行的时间。人眼分辨率 ~10ms，而本机延迟只有几十~几百 µs，所以「看起来同步」；只有纳秒级时间戳才能照出来（实战中测到一次 340µs）。
2. **量级**：
   - 本机（共享内存，CycloneDDS 默认）：**几十 ~ 几百 µs**
   - 本机（UDP loopback）：~100µs ~ 1ms
   - 跨机器（1G 以太网）：几百 µs ~ 几 ms
   - 尾延迟（99.9%）：因调度抖动可能冲到 ms 级
   - 直觉：**本机亚毫秒，跨机毫秒级。**
3. **消息走过的链路（6 步）**：序列化 → DDS 写入 → 传输（共享内存 / UDP / 网络）→ DDS 接收 → 反序列化 → executor 调度回调。每步 µs 级，累加即总延迟。
4. **影响因素**：消息大小（越大越慢）/ 传输方式（共享内存 < UDP < 跨机网络）/ QoS（`Reliable` 有 ACK 握手，比 `Best Effort` 慢）/ executor 单线程回调串行（**最大变量**）/ 系统负载与抢占 / 跨机网络抖动。
5. **工程问题**：
   - ① 控制闭环稳定性：延迟 = 相位滞后，过大或过抖会超调、震荡、甚至失稳
   - ② 抖动比固定延迟致命：固定延迟可预测、可补偿，随机抖动不可补偿
   - ③ 数据新鲜度 / 时滞：延迟 × 移动速度 = 位置偏差（如 100ms × 1m/s = 10cm）
   - ④ 队列积压：生产 > 消费时，延迟随时间越涨越大
   - ⑤ 跨机时钟同步：多机融合要求时间戳对齐
6. **缓解方向**：回调快进快出 / 能容忍丢用 `Best Effort` + 小消息 / 本机共享内存 / 慢回调隔离（callback group / 多线程 executor）/ 关键控制用 QoS `Deadline` 监控。

> **Note（连接 / 深化）：**
> - 连接：executor 单线程串行是延迟最大变量，见 [[N009 Executor事件循环]]；QoS 的 Reliable / Best Effort 见 [[N002 QoS队列深度10]]；DDS 传输层见 [[N011 ROS2分层架构]]。
> - 深化：延迟分「固定延迟」（可预测、可补偿）和「抖动」（随机、不可补偿），工程上最怕抖动；端到端延迟是**软实时**指标，ROS 2 默认非硬实时。

## 总结

**本质：** 话题通信不是同步，而是「发布 → 序列化 → DDS 传输 → 反序列化 → 调度回调」的异步链路，存在端到端延迟；本机亚毫秒、跨机毫秒级，受消息大小 / 传输方式 / QoS / 回调串行影响；工程上延迟与抖动会影响控制稳定性与数据新鲜度。
