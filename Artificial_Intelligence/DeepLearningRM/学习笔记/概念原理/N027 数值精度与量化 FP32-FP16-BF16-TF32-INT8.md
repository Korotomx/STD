FP32 是基准；FP16/BF16 是换一种更小的浮点，不用校准但会掉一点精度；INT8 是用 256 个整数近似浮点，必须校准，收益最大风险也最大；TF32 不是存储格式，只是 FP32 在 Tensor Core 上的加速模式。

## 两个词先分清

| 词 | 含义 | 典型格式 |
| ---- | ---- | ---- |
| **降低精度** | 还是浮点，只是尾数/指数位变少 | FP32 → FP16 / BF16 |
| **量化** | 连续浮点映射到离散整数，需要 scale | FP32 → INT8 |

所以「用 FP16 推理」是半精度推理，不是量化；「用 INT8 推理」才是量化推理。日常口语把两者都叫量化，机制完全不同。

## 浮点数怎么存

```
value = (-1)^sign × 1.mantissa × 2^(exponent - bias)
```

- 符号位 sign：正负
- 指数位 exponent：能表示多大/多小的范围
- 尾数位 mantissa：有多少位有效数字

**指数决定「能不能装下」，尾数决定「装得准不准」。**

## 格式对照

| 格式 | 总位数 | 符号 | 指数 | 尾数 | 有效十进制位 | 范围 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| FP64 | 64 | 1 | 11 | 52 | ~15~16 位 | ±1.8e308 |
| **FP32** | 32 | 1 | 8 | 23 | ~7 位 | ±3.4e38 |
| **TF32** | 19（仅计算） | 1 | 8 | 10 | ~3 位 | 同 FP32 |
| **FP16** | 16 | 1 | 5 | 10 | ~3 位 | 最大 65504，最小正规数 6.1e-5 |
| **BF16** | 16 | 1 | 8 | 7 | ~2~3 位 | 同 FP32 |
| **INT8** | 8 | — | — | — | 256 档 | −128 ~ 127 |

必须记住：FP16 最大 **65504**，超过就 `inf`；FP16 最小正规数约 **6.1e-5**，更小的进入非正规区（最小约 6e-8）；FP32 约 **7 位十进制**；INT8 只有 **256 档**，相邻间隔由 `scale` 决定。

### FP16：尾数够，指数不够

FP32 的尾数 23→10 位、指数 8→5 位。

```
FP32: 0.123456789
FP16: 0.123474…
```

精度约 3 位十进制，对卷积、检测通常够用；但超过 65504 溢出，很小的梯度/激活下溢成 0。适合卷积为主、数值范围可控的推理；Softmax、LayerNorm、大激活、loss 计算要小心。

### BF16：指数够，尾数不够

保留 FP32 的 8 位指数，尾数砍到 7 位。范围和 FP32 一样，不容易溢出；精度只有 2~3 位十进制，比 FP16 还低。训练常用 BF16 + FP32 master weights，因为不用担心溢出。

**FP16 精度高但范围小；BF16 范围大但精度低。**

### TF32：计算模式，不是格式

Ampere 之后引入：数据在显存里**仍是 FP32**，进 Tensor Core 做矩阵乘时尾数临时截到 10 位，结果累加仍是 FP32。所以它不是 ONNX 里的数据类型，不能导出「TF32 模型」；TensorRT 默认允许 FP32 卷积走 TF32（可显式关闭）。它常被误认为 FP16，其实是「FP32 的加速档」。

## INT8：真正的量化

### 映射公式

```
real = scale × (q - zero_point)
q    = clamp(round(real / scale) + zero_point, -128, 127)
```

| 参数 | 作用 |
| ---- | ---- |
| `scale` | 一个整数档代表多少浮点值 |
| `zero_point` | 浮点 0 对应哪个整数（对称量化时 = 0） |
| `clamp` | 超出范围就截断 |

例：`scale=0.5, zero_point=0`

```
real 1.2 → q = round(1.2/0.5) = 2 → 反量化 1.0
real 1.3 → q = round(1.3/0.5) = 3 → 反量化 1.5
```

一档 0.5，误差自然出现。

### per-tensor vs per-channel

| 方式 | 含义 | 常用在 |
| ---- | ---- | ---- |
| per-tensor | 整个张量共用一个 scale | 激活值 |
| per-channel | 每个输出通道一个 scale | 卷积权重 |

per-channel 能适应不同通道的数值范围，精度明显更好。

### 校准 calibration

激活范围事先不知道，要拿一批**有代表性的数据**跑 FP32，统计每层输出分布再选 scale：

| 方法 | 思路 |
| ---- | ---- |
| min-max | 取最大最小，简单但怕离群值 |
| percentile | 截掉极端百分位 |
| entropy | 量化前后分布熵最小 |

校准集必须和真实部署数据同分布：拿白天图片校准、夜里推理，精度一定崩。

### Q/DQ

现代 TensorRT（含 11）要求**显式 Q/DQ**：`QuantizeLinear`（float→int8，写入 scale）和 `DequantizeLinear`（int8→float，写回 scale）把 scale 固化进 ONNX 图。老版本「给个 calibrator 自动量化」在 strongly-typed 模式下已不用。

## 训练 AMP ≠ 部署量化

| | 训练 AMP | 部署 FP16/INT8 |
| ---- | ---- | ---- |
| 目的 | 省显存、加速训练 | 省显存、加速推理 |
| 反向传播 | 有 | 无 |
| 权重 | FP32 master + FP16/BF16 计算副本 | 直接存低精度 |
| 需要校准 | 否 | FP16 否，INT8 是 |
| 精度控制 | loss scaling 防梯度下溢 | 验证集 + 误差分析 |

训练用 AMP 不代表部署就是 FP16；部署精度要单独决定、单独验证。

## 三种部署精度对比

| | FP32 | FP16 | INT8 |
| ---- | ---- | ---- | ---- |
| 每元素字节 | 4 | 2 | 1 |
| 显存/带宽 | 基准 | 约 1/2 | 约 1/4 |
| 计算速度 | 基准 | 约 1.5~2× | 约 2~4× |
| 需要校准 | 否 | 否 | **是** |
| 精度损失 | 无 | 很小 | 可能明显 |
| 主要风险 | 慢 | 溢出/下溢 | 离群值、回归精度 |
| 典型用途 | 基线、对照 | 部署默认 | 极致性能 |

速度倍率是数量级参考，实际取决于模型、GPU、batch、是否 memory-bound。

## groundzero 的 FP16 实测

之前 engine 都是 FP32（`images (1,3,640,640) FLOAT`，`output0 (1,300,30) FLOAT`，229 个权重全 FLOAT）。用 `model.export(format="engine", quantize=16)` 生成 FP16：

| 文件 | 精度 | 大小 |
| ---- | ---- | ---- |
| `best_fp32.engine` | FP32 基线 | 12.2 MB |
| `best.engine` | FP16 混合 | 7.7 MB |
| `best.fp16.onnx` | FP16 ONNX（ModelOpt AutoCast） | 5.3 MB |

ModelOpt 转换：**404/437 节点（92.45%）转 FP16**；检测头里坐标范围超过 `[-512,512]` 的 Concat 节点自动保留 FP32，避免坐标精度损失。

### 精度账

FP16 在 `[512,1024)` 区间相邻可表示值间隔 **0.5**：640 空间里坐标舍入误差最多约 **0.25 px**，逆映射回 4096 原图乘 `1/r=6.4`，约 **1.6 px**。

同一张 4096×3072 val 图：

| 指标 | 差异 |
| ---- | ---- |
| 框坐标最大差 | 0.86 px |
| 关键点坐标最大差 | **1.39 px** |
| 最高置信度 | 0.91358 vs 0.91357 |

val 集 117 张：

| 指标 | FP32 | FP16 | 差异 |
| ---- | ---- | ---- | ---- |
| box mAP50 | 0.98933 | 0.98893 | −0.0004 |
| box mAP50-95 | 0.87417 | 0.87258 | −0.0016 |
| pose mAP50 | 0.98933 | 0.98893 | −0.0004 |
| pose mAP50-95 | 0.96911 | 0.96871 | −0.0004 |

精度损失可忽略，关键点仍在 1~2 px 量级。

### 速度账

| 阶段 | FP32 | FP16 |
| ---- | ---- | ---- |
| 预处理 | 1.16 ms | 1.05 ms |
| engine（含拷贝/分配/同步） | 3.79 ms | 3.44 ms |
| 后处理 | 0.14 ms | 0.15 ms |
| **端到端** | **5.10 ms（196 FPS）** | **4.35 ms（230 FPS）** |

trtexec 测**纯 GPU kernel**：

| engine | GPU Compute Time |
| ---- | ---- |
| FP32 | 1.385 ms |
| FP16 | **0.690 ms（约 2×）** |

端到端只快 15%，因为瓶颈在 Python 推理循环的固定开销：每次 `torch.from_numpy(...).cuda()`、`torch.empty(...)`、H2D/D2H 拷贝和 `synchronize`。想继续提速，优先预分配 buffer、复用显存、减少同步，而不是继续压精度。

### INT8 的额外风险

关键点回归对数值敏感：输出头最好保留 FP16/FP32；校准集覆盖不同光照、角度、距离；必须看每个关键点的像素误差，而不只是 mAP。

## TensorRT 11 下的操作路线

### FP16

```
best.pt
  → 导出 FP32 ONNX
  → 转 FP16 ONNX（ModelOpt AutoCast 或 onnxconverter-common）
     · keep_io_types=True，输入输出仍保留 FP32
     · Softmax / LayerNorm 等算子放进 block list
  → trtexec --onnx=best_fp16.onnx --saveEngine=best_fp16.engine
  → val 集对比
```

TensorRT 11 是 strongly-typed，**没有 `--fp16` 开关**，精度必须写进 ONNX。groundzero 用 Ultralytics 一步封装：

```python
from ultralytics import YOLO

YOLO("runs/pose/train-4/weights/best.pt").export(
    format="engine",     # 'trt' / 'tensorrt' 是别名
    quantize=16,         # 16 = FP16；8 = INT8（需 data 校准）
    imgsz=640, batch=1,
    workspace=2,         # GiB
    device=0,
)
```

第一次运行会自动安装 `nvidia-modelopt[onnx]>=0.44`。

### INT8

```
FP32 ONNX → 插入 Q/DQ（ModelOpt pytorch-quantization 或 ONNX Runtime 工具）
          → 校准集跑一遍，确定每层 scale → trtexec build → val 对比
```

### 验证顺序

1. FP32 engine 跑基线：mAP、关键点像素误差、端到端耗时
2. 换 FP16：同一 val 集逐项对比
3. FP16 达标且速度仍不够，再考虑 INT8
4. 每次只改一个变量

## 坑与边界

| 现象 | 原因 |
| ---- | ---- |
| FP16 engine 输出 `inf`/`nan` | 激活超过 65504，或下溢 |
| FP16 精度突然崩 | Softmax/LayerNorm 等敏感算子没保留 FP32 |
| INT8 精度崩 | 校准集不代表真实分布，或离群值拉大 scale |
| 检测框还行、关键点全偏 | 回归头被量化，坐标精度不够 |
| 加了 `--fp16` 没效果 | TensorRT 11 strongly-typed，开关已移除 |
| 速度没提升 | 模型 memory-bound，或瓶颈在前后处理/拷贝 |
| 换设备后 engine 不能用 | engine 绑定 GPU 架构、TRT 版本、输入 shape |

## 总结

指数决定范围、尾数决定精度；FP16 尾数够但范围小，BF16 范围够但精度低；TF32 是 FP32 的 Tensor Core 加速模式，不是格式。FP16 不用校准、INT8 必须校准，INT8 的 scale 来自数据分布，校准集错了精度必崩。训练 AMP 与部署精度是两件事。groundzero 实测 FP16：engine 12.2→7.7 MB，92.45% 节点转 FP16；纯 GPU 1.385→0.690 ms，端到端 5.10→4.35 ms，pose mAP50-95 仅降 0.0004，关键点最大差 1.39 px。
