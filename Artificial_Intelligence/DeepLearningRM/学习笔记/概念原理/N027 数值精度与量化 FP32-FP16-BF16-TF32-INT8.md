## 一句话

**FP32 是基准；FP16/BF16 是“换一种更小的浮点”，不用校准但会掉一点精度；INT8 是“用 256 个整数近似浮点”，必须校准，收益最大、风险也最大；TF32 不是存储格式，只是 FP32 在 Tensor Core 上的加速模式。**

## 0. 先分清两个词

| 词 | 含义 | 典型格式 |
| ---- | ---- | ---- |
| **降低精度** | 还是浮点，只是尾数/指数位变少 | FP32 → FP16 / BF16 |
| **量化** | 把连续浮点映射到离散整数，需要 scale | FP32 → INT8 |

所以严格说：

- “用 FP16 推理” = 半精度推理，**不是量化**
- “用 INT8 推理” = 量化推理
- 日常口语里把两者都叫“量化”，但机制完全不同

## 1. 浮点数是怎么存的

```
value = (-1)^sign × 1.mantissa × 2^(exponent - bias)
```

三个部分：

- **符号位 sign**：正负
- **指数位 exponent**：决定能表示多大/多小的范围
- **尾数位 mantissa**：决定有多少位有效数字（精度）

一个直觉：

> **指数决定“能不能装下”，尾数决定“装得准不准”。**

## 2. 常见格式对照

| 格式 | 总位数 | 符号 | 指数 | 尾数 | 有效十进制位 | 表示范围 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| FP64 | 64 | 1 | 11 | 52 | ~15~16 位 | ±1.8e308 |
| **FP32** | 32 | 1 | 8 | 23 | ~7 位 | ±3.4e38 |
| **TF32** | 19（仅计算） | 1 | 8 | 10 | ~3 位 | 同 FP32 |
| **FP16** | 16 | 1 | 5 | 10 | ~3 位 | 最大 **65504**，最小正规数 6.1e-5 |
| **BF16** | 16 | 1 | 8 | 7 | ~2~3 位 | 同 FP32 |
| **INT8** | 8 | — | — | — | 256 个整数档位 | -128 ~ 127 |

几个必须记住的数：

- FP16 最大 **65504**，超过就 `inf`
- FP16 最小正规数约 **6.1e-5**，更小的数进入非正规区，最小约 6e-8
- FP32 有效数字约 **7 位十进制**
- INT8 只有 **256 档**，相邻档位的间隔由 `scale` 决定

## 3. FP16：尾数够，指数不够

FP16 把 FP32 的尾数从 23 位砍到 10 位、指数从 8 位砍到 5 位。

```
FP32: 0.123456789
FP16: 0.123474…
```

- 精度大约 3 位十进制，对卷积、检测通常够用
- 但范围小：激活值一旦超过 65504 就溢出
- 很小的梯度/激活会下溢成 0

**适合**：卷积为主、数值范围可控的推理。
**小心**：Softmax、LayerNorm、大激活、loss 计算。

## 4. BF16：指数够，尾数不够

BF16 保留 FP32 的 8 位指数，只把尾数砍到 7 位。

- 范围和 FP32 一样，不容易溢出
- 精度只有 2~3 位十进制，比 FP16 还低
- 训练时常用 BF16 + FP32 master weights，因为不用担心溢出

一句话：**FP16 精度高但范围小；BF16 范围大但精度低。**

## 5. TF32：不是格式，是计算模式

TF32 是 NVIDIA 在 Ampere 之后引入的 Tensor Core 计算模式：

- 数据在显存里**仍然是 FP32**
- 进入 Tensor Core 做矩阵乘时，尾数临时截到 10 位
- 结果累加仍是 FP32

所以：

- 它不是 ONNX 里的数据类型
- 不能导出成 “TF32 模型”
- TensorRT 默认允许 FP32 卷积走 TF32（可显式关闭）

**它常被误认为 FP16，其实是“FP32 的加速档”。**

## 6. INT8：真正的量化

### 6.1 映射公式

```
real = scale × (q - zero_point)
q    = clamp(round(real / scale) + zero_point, -128, 127)
```

| 参数 | 作用 |
| ---- | ---- |
| `scale` | 一个整数档位代表多少浮点值 |
| `zero_point` | 浮点 0 对应哪个整数（对称量化时 = 0） |
| `clamp` | 超出范围就截断，避免溢出 |

例子：`scale = 0.5`，`zero_point = 0`

```
real 1.2  → q = round(1.2 / 0.5) = 2  → 反量化 1.0
real 1.3  → q = round(1.3 / 0.5) = 3  → 反量化 1.5
```

一个档位 0.5，误差自然就来了。

### 6.2 per-tensor vs per-channel

| 方式 | 含义 | 用在哪 |
| ---- | ---- | ---- |
| **per-tensor** | 整个张量共用一个 scale | 激活值常用 |
| **per-channel** | 每个输出通道一个 scale | 卷积权重常用 |

per-channel 能适应不同通道的数值范围，精度明显更好。

### 6.3 校准 calibration

激活值的范围事先不知道，需要拿一批**有代表性的数据**跑 FP32，统计每层输出的分布，再选 scale：

| 方法 | 思路 |
| ---- | ---- |
| min-max | 取最大最小值，简单但怕离群值 |
| percentile | 截掉极端百分位，减少离群值影响 |
| entropy | 让量化前后分布熵最小 |

校准集必须和真实部署数据同分布：拿白天图片校准、夜里推理，精度一定崩。

### 6.4 Q/DQ

现代 TensorRT（含 11）要求 **显式 Q/DQ**：

```
QuantizeLinear   (float → int8，写入 scale)
DequantizeLinear (int8 → float，写回 scale)
```

这两个节点把 scale 固化进 ONNX 图，TensorRT 看到它们才知道哪里该量化、用什么 scale。老版本的“给个 calibrator 自动量化”在 strongly-typed 模式下已经不用了。

## 7. 训练时的 AMP ≠ 部署量化

| | 训练 AMP | 部署 FP16/INT8 |
| ---- | ---- | ---- |
| 目的 | 省显存、加速训练 | 省显存、加速推理 |
| 是否有反向传播 | 有 | 无 |
| 权重 | FP32 master + FP16/BF16 计算副本 | 直接存低精度 |
| 是否需要校准 | 否 | FP16 否，INT8 是 |
| 精度控制 | loss scaling 防梯度下溢 | 验证集 + 误差分析 |

训练用 AMP 不代表部署就是 FP16；部署精度要单独决定、单独验证。

## 8. 三种部署精度对比

| | FP32 | FP16 | INT8 |
| ---- | ---- | ---- | ---- |
| 每元素字节 | 4 | 2 | 1 |
| 显存/带宽 | 基准 | 约 1/2 | 约 1/4 |
| 计算速度 | 基准 | 约 1.5~2× | 约 2~4× |
| 需要校准 | 否 | 否 | **是** |
| 精度损失 | 无 | 很小 | 可能明显 |
| 主要风险 | 慢 | 溢出/下溢 | 离群值、回归精度 |
| 典型用途 | 基线、对照 | 部署默认 | 极致性能 |

> 速度倍率是数量级参考，实际取决于模型、GPU、batch、是否 memory-bound。

## 9. 对 groundzero 的意义

### 9.1 当前是什么精度

2026-10-22 21:04 之前，groundzero 的 engine 都是 **FP32**：

```
images  (1,3,640,640) FLOAT
output0 (1,300,30)    FLOAT
ONNX 权重：229 个 FLOAT，无 FP16 Cast
```

之后用 Ultralytics 的 `model.export(format="engine", quantize=16)` 生成了 FP16 engine：

| 文件 | 精度 | 大小 |
| ---- | ---- | ---- |
| `best_fp32.engine` | FP32（备份的基线） | 12.2 MB |
| `best.engine` | **FP16 混合精度** | 7.7 MB |
| `best.fp16.onnx` | FP16 ONNX（ModelOpt AutoCast 产物） | 5.3 MB |

ModelOpt 转换日志：**404/437 个节点（92.45%）转成 FP16**；检测头里坐标范围超过 `[-512, 512]` 的 Concat 节点被自动保留为 FP32，避免坐标精度损失。

### 9.2 换 FP16 的精度账（已实测）

FP16 在 `[512, 1024)` 区间的相邻可表示值间隔是 **0.5**：

- 640 输入空间里，坐标舍入误差最多约 **0.25 px**
- 逆映射回 4096 原图要乘 `1/r = 6.4`
- 对应原图误差约 **1.6 px**

实测（同一张 4096×3072 val 图，FP32 vs FP16）：

| 指标 | 差异 |
| ---- | ---- |
| 框坐标最大差 | 0.86 px |
| 关键点坐标最大差 | **1.39 px** |
| 最高置信度 | 0.91358 vs 0.91357 |

val 集 117 张对比：

| 指标 | FP32 | FP16 | 差异 |
| ---- | ---- | ---- | ---- |
| box mAP50 | 0.98933 | 0.98893 | -0.0004 |
| box mAP50-95 | 0.87417 | 0.87258 | -0.0016 |
| pose mAP50 | 0.98933 | 0.98893 | -0.0004 |
| pose mAP50-95 | 0.96911 | 0.96871 | -0.0004 |

结论：**精度损失可以忽略**，关键点仍在 1~2 px 量级。

### 9.3 换 FP16 的速度账（已实测）

| 阶段 | FP32 | FP16 |
| ---- | ---- | ---- |
| 预处理 | 1.16 ms | 1.05 ms |
| engine（脚本内，含拷贝/分配/同步） | 3.79 ms | 3.44 ms |
| 后处理 | 0.14 ms | 0.15 ms |
| **端到端** | **5.10 ms（196 FPS）** | **4.35 ms（230 FPS）** |

但用 trtexec 测**纯 GPU kernel**：

| engine | GPU Compute Time |
| ---- | ---- |
| FP32 | 1.385 ms |
| FP16 | **0.690 ms（约 2×）** |

差异来自 Python 推理循环里的固定开销：每次 `torch.from_numpy(...).cuda()`、`torch.empty(...)`、H2D/D2H 拷贝和 `synchronize`，这些不会因为 FP16 变快。所以：

- **纯引擎算力**：FP16 正好约 2 倍
- **端到端**：只快 15%，因为瓶颈在拷贝和 CPU 前后处理

想进一步提速，优先预分配输入输出 buffer、复用显存、减少同步，而不是继续压精度。

### 9.4 换 INT8 的额外风险

关键点回归对数值很敏感：

- 输出头最好保留 FP16/FP32
- 校准集要覆盖不同光照、角度、距离
- 必须看每个关键点的像素误差，而不只是 mAP

## 10. TensorRT 11 下的实际操作路线

### 10.1 FP16

```text
best.pt
  → 导出 FP32 ONNX
  → 转 FP16 ONNX（ModelOpt AutoCast 或 onnxconverter-common）
     · keep_io_types=True，输入输出仍保留 FP32
     · Softmax / LayerNorm 等算子放进 block list
  → trtexec --onnx=best_fp16.onnx --saveEngine=best_fp16.engine
  → val 集对比
```

TensorRT 11 是 strongly-typed，**没有 `--fp16` 开关**；精度必须写进 ONNX。

groundzero 实际用的是一步封装（Ultralytics 内部完成 ONNX → ModelOpt → build）：

```python
from ultralytics import YOLO

YOLO("runs/pose/train-4/weights/best.pt").export(
    format="engine",     # 'trt' / 'tensorrt' 是别名
    quantize=16,         # 16 = FP16 混合精度；8 = INT8（需 data 校准）
    imgsz=640,
    batch=1,
    workspace=2,         # GiB
    device=0,
)
```

输出 `best.engine`。第一次运行会自动安装 `nvidia-modelopt[onnx]>=0.44`。

### 10.2 INT8

```text
FP32 ONNX
  → 插入 Q/DQ（TensorRT ModelOpt pytorch-quantization 或 ONNX Runtime 工具）
  → 用校准集跑一遍，确定每层 scale
  → trtexec build
  → val 集对比
```

### 10.3 验证顺序

1. FP32 engine 跑基线：mAP、关键点像素误差、端到端耗时
2. 换 FP16：同一 val 集，逐项对比
3. FP16 达标且速度仍不够，再考虑 INT8
4. 每次只改一个变量，否则不知道是谁起的作用

## 11. 常见坑

| 现象 | 原因 |
| ---- | ---- |
| FP16 engine 输出 `inf` / `nan` | 激活超过 65504，或下溢 |
| FP16 精度突然崩 | Softmax/LayerNorm 等敏感算子没保留 FP32 |
| INT8 精度崩 | 校准集不代表真实分布，或离群值拉大 scale |
| 检测框还行、关键点全偏 | 回归头被量化，坐标精度不够 |
| 加了 `--fp16` 没效果 | TensorRT 11 strongly-typed，该开关已移除 |
| 速度没提升 | 模型是 memory-bound，或瓶颈在前后处理/拷贝 |
| 换设备后 engine 不能用 | engine 绑定 GPU 架构、TensorRT 版本、输入 shape |

## 术语表

| 术语 | 中文 | 一句话 |
| ---- | ---- | ---- |
| precision | 精度 | 一个数用多少位表示 |

| FP16 | 半精度 | 16 位浮点，范围小、精度约 3 位 |
| BF16 | 脑浮点 | 16 位，范围同 FP32、精度更低 |

| INT8 | 8 位整数 | 256 档，需要 scale |
| quantization | 量化 | 浮点 → 整数 |
| dequantization | 反量化 | 整数 → 浮点 |

| per-tensor | 逐张量 | 整个张量共用一个 scale |
| per-channel | 逐通道 | 每个通道一个 scale |

| master weights | 主权重 | 训练时保留的 FP32 权重副本 |

## 总结

1. **指数决定范围，尾数决定精度**；FP16 尾数够但范围小，BF16 范围够但精度低。
2. **TF32 不是格式**，是 FP32 在 Tensor Core 上的加速模式，数据仍以 FP32 存储。
3. **FP16 不用校准，INT8 必须校准**；INT8 的 scale 来自数据分布，校准集错了精度必崩。
4. **训练 AMP 和部署精度是两件事**，部署精度要单独验证。
5. **groundzero 已完成 FP16 实测**：engine 12.2 MB → 7.7 MB，92.45% 节点转 FP16；纯 GPU 1.385 ms → 0.690 ms（约 2×），端到端 5.10 ms → 4.35 ms；pose mAP50-95 仅从 0.96911 降到 0.96871，关键点最大差 1.39 px。
