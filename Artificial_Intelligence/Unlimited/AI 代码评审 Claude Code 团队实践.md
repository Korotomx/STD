# AI 代码评审 · Claude Code 团队实践

**时间:** 2026-10-22 整理
**来源:** Anthropic 官方博客《How the Claude Code team does code review》（claude.dev）
**原文:** [[How the Claude Code team does code review]]
**标签:** #代码评审CodeReview #AI编程AgenticCoding #ClaudeCode #工程实践EngineeringPractice #风险管理RiskTiering
**关联:** 工程实践类，归 Unlimited；与 6.S191 课程无直接关系

## 一句话

当 **90% 的代码由 Claude 写**时，Claude Code 团队没有取消评审，而是把**大部分阅读交给机器**：评审从「PR 末尾的人工关卡」变成「写代码时全程运行的拼写检查」；人的时间只花在**只有人能判断的事**上，同时用 **revert / incident 率**当护栏，确保省下的时间没有变成事后救火。

## 实际情况

### 0. 背景：代码量翻倍，回滚率反而下降

- Claude 写了 Claude Code 自身约 **90%** 的代码。
- 6→9 月：合并的 PR 数**翻倍多**，被回滚的 PR 占比**下降 40%+**。
- Anthropic 单体仓库每天落地的变更从 5 月的约 **2,500** 涨到 9 月的 **30,000+**。
- 结论：**没有减少评审，而是把「读」移给机器，把「判断」留给人，并投资「快速撤销」的能力。**

### 1. 重新定义评审的目的

评审有两个职责：

1. **在发布前发现并修复问题**（本文重点）；
2. **在团队内建立共享上下文与代码理解**（文末再谈）。

团队认为「**有人读过代码吗？**」是一个不精确的代理指标。更好的问法是：

> 这次变更**可能出什么问题**？应该由**哪种检查**（自动或人工）来抓？

这改变了评审发生的**时间点**：过去是「写完 → 开 PR → 等同事」的末端关卡；现在评审**持续运行**，更像写代码时的拼写检查。多数变更在人类看到之前，已经被 Claude 评审并修过至少一轮。

### 2. 稀缺资源：人的时间与注意力

- 人的成本有两头：**评审花的时间** + **坏代码出事后修复花的时间**。只砍第一头，时间会从第二头冒出来。
- 目标：大多数 PR **最多一个人类 in the loop**（可以是作者本人），且 **revert / incident 率不上升**。
- 度量：每个 PR 的人类批准数（中位数 + P95）、人类评论数、PR 等人时长。
- **护栏**：revert 率与 incident 率——它们一升，就说明时间只是被**转移**了，没有真正省下。

### 3. 一次变更的七层流程

| 层 | 做什么 | 谁/什么 |
| ---- | ---- | ---- |
| 1. PR 之前 | Claude 跑测试 / 构建 / 截图对比；**fresh context 的 subagent** 审 diff；内部 skills（找 bug / 简化 / 端到端检查） | Claude + 作者 |
| 2. 每个 PR | AI 评审：对照**整个仓库**和 PR 声明的意图，判断「是否解决问题 / 是否契合系统 / 是否弄坏别处」 | Claude |
| 3. 安全评审 | 独立的安全检查；**任一未关闭的发现都阻塞合并** | 自动 |
| 4. CI | lint、类型检查、全平台测试、构建；PR 模板要求填「怎么测的 / 风险 / 怎么回滚」 | CI |
| 5. 人工批准 | 按**风险等级**决定 0 / 1 / 2 人 | 人 |
| 6. 合并 | merge queue 在最新 main 上**重跑全部检查**；feature flag + 内部先用 + 分渠道发布 | 自动 |
| 7. 合并后 | 快速发现、快速回滚；on-call 轮值；事故复盘问「哪一层本该拦住」 | 人 + 监控 |

#### 第 1 层：PR 之前就验证

- 给 Claude **可运行的东西**（测试、构建、设计稿截图），要求它**展示输出**，而不是口头说「做完了」。
- 再让一个 **fresh context 的 subagent** 审 diff——不带着实现时的上下文，更容易发现问题。
- Boris Cherny（Claude Code 作者）称「给 Claude 一个验证自己工作的方式」大概是获得好结果**最重要的一件事**，能让最终质量提升 **2~3 倍**。
- 自动评审反复指出同一类问题时，**从源头修**：改 skill、加 lint 规则、更新 `CLAUDE.md` / `REVIEW.md`。
  - `CLAUDE.md`：项目是什么（技术栈、约定、目标与非目标），保持简短，细节指向其他文档。
  - `REVIEW.md`：由 code owner 写「这部分代码什么最重要」；好的版本很短，会说明「失败长什么样」（文档 = 说谎，配置 = 路由错），限制 nit 数量，列出可跳过路径，要求**给出文件和行号作为证据**。

#### 第 2 层：每个 PR 都跑 AI 评审

- 评审会读 diff、整个仓库和 PR 意图；修 bug 时重点找**根因**。
- 数据：研究预览上线后，内部 PR 中获得**实质性评审意见**的比例从 **16% → 54%**；超过 1,000 行的大 PR 大多能发现问题，小 PR 大多干净返回。
- 每个仓库可选 **Quick / Standard / Deep**；「漏一个 bug 的代价 > 多花评审时间」的地方才用 Deep。
- **发现要先被其他 agent 验证**：多个 agent 并行找 bug → 另一组 agent 对每条发现**投票** → 票数够才发布；纯风格 / 诊断 / 清理类直接丢弃（这些过滤规则在自己的 PR 上做过 A/B）。
- 剩下的以内联评论按**严重程度**排序，并标注 **Important / Nit / Pre-existing**——不是这个 PR 引入的 bug，不应看起来像作者的锅。
- **每条发现都必须有回应**：修掉，或写理由 resolve。经常是 agent 夜里把修复做了，作者早上回来看到 PR 已经又过了一轮。

#### 第 3~4 层：安全与 CI 都能阻塞

- 安全评审的发现同样**阻塞合并**；修掉或写短理由关闭（用于清除误报）；后续 commit 修好了会自动清除。
- CI 是常规项：lint、类型、全平台测试、构建。一个典型 CLI PR 在被人看之前可能跑**几十项检查**。
- PR 模板要求回答：**怎么测的、风险是什么、怎么撤销**。Claude 可以代填，但**提出变更的人要签字确认**。

#### 第 5 层：人工批准按风险缩放

| 风险 | 例子 | 需要的人类批准 |
| ---- | ---- | ---- |
| 低 | 文档、文案、内部功能、flag 后的增量变更 | 自动评审 + 安全检查全绿后**不需要**人 |
| 中 | 普通产品变更；缓存、自动更新器、system prompt 等敏感区 | **1 人** |
| 高 | 最高风险代码 + 永远需要两人的路径 | **2 人** |

- **等级由变更决定，不由作者决定**：分类器读变更定级；第二个分类器判断「即使等级说不用，这次是否仍需一个人」。
- 某些路径**永远需要人**：owner 标记的敏感路径、任何 CI workflow 文件。
- **只有受信任作者**（主要是团队自己）能走轻量路径；其他人需要第二人批准。**agent 的批准永远不能顶替人的名额。**
- **提出变更的人对结果负责**：agent 写的 PR，指挥 agent 的人算作必需评审人之一，和亲手敲代码一样。
- **批准只对某个 commit 有效**：来了系统无法担保的新 commit（agent push、手工解决的 merge），必须重新批准。

#### 第 6 层：合并队列、flag、渐进发布

- **merge queue** 在最新 main 上重跑检查，防止两个单独能过的 PR 合起来弄坏 main。
- 新行为通常先藏在 **feature flag** 后给 Anthropic 员工用；公开版本先发 `latest` 渠道，`stable` 渠道随后。

#### 第 7 层：快速发现、快速回滚

- 仍会有漏网之鱼，最后一层是**尽快抓出来**：flag 不用部署就能关；团队有每周 on-call；事故复盘会问「哪一层本该拦住」。
- 目前还没有「指标一动就自动收紧审批」的 **circuit breaker**，工程师希望在更多「零人工合并」之前补上。
- 有同事说：**放慢确实能降低错误率，但主要是因为你做得更少**。团队宁愿把「发现和修复」变快。

### 4. 让评审者越用越好的闭环

- **事故变成 eval**：把历史上导致事故的 PR（连同 fix-forward / revert）收集起来，让熟悉该代码的工程师确认 bug 与位置；reviewer 每天跑这套 eval。每次改 prompt / 工具 / 模型，都用整套 eval 重新打分。
- **用人的行为度量噪声**：按作者对评论的反应分类（修了 / 说它错了 / 说这是有意为之 / 觉得不重要）；再拿已知干净的 PR 跑 reviewer，统计「会导致有害改动」的误报率。
  - 优先级写死：**先抓真 bug，再减评审轮数**。
  - **噪声对 agent 作者更贵**：人能一秒无视一个 nit，agent 会去修 → 多一个 commit → 多一轮评审。
- **评审必须收敛**：agent 作者 + agent 评审可以无限互相忙碌。有一个 CLI PR 一夜之间跑了 **50+ 轮**评审与修复，最后被作者叫停。
  - 对 reviewer 反复指出的内容做 `git blame`：约 **59%** 是 reviewer 第一轮就存在的旧代码——它不是每轮发现新 bug，而是每轮多翻出几个旧 bug。
  - 团队自己也把它搞坏了：习惯性默认跑多轮。现在同时跟踪 **rounds-to-pass** 与召回率，并改了重审策略：
    - **轮数上限**：3 轮后，reviewer 要求作者停下来重新考虑方案；
    - 前几轮之后，**只审新 diff**；
    - **按 bug 类别标记**，让作者一次修掉所有同类实例，而不是一行；
    - **不重复**已发过的发现。
- reviewer 还会**每晚跑存量代码**，在旧 bug 冒出来之前先抓。

### 5. 人还在哪些环节

把资深工程师从深度工作中拽出来抓一个例行错误，成本远高于自动评审。人仍然负责：

- **决定要不要做**：方向、品味、范围（「我们到底该不该做这件事？」）。
- **审高风险代码**：计费、自动更新器、CI workflow。
- **审架构**：会被人模仿的模式。
- **读证据**：测试输出、跑过的命令与返回、截图、reviewer 的发现。**如果你说不出这些检查会漏什么，就该要一次真正的评审，而不是快速点个 approve。**
- **对结果负责**：不管谁敲的代码，发布出去的每个变更都有人 accountable。

### 6. 机器读代码后，团队怎么建立共享理解

- 没有正式流程，也没人能在脑子里装下整个 Claude Code。
- 想理解某块代码时，**让 Claude 针对那个切片写一份讲解**——几分钟完成，且反映**今天的代码**。
- 更进一步：让 Claude 做一个小工具，把这块代码**可视化**，按个人习惯的方式教自己。
- 团队认为这比逐行读琐碎 diff 更值：一行文案改动几乎学不到东西，而为「你马上要改的模块」写讲解能学到很多。
- 默认在**公开 Slack 频道**工作，也能看到别人正在做什么。

### 7. 「你合入，你负责」

- 小 / 中变更出问题，默认由**合入者**去修。
- 不让它变糟的机制：**变更小**（易审、易调、易回滚）；**一切可逆**（flag、revert、分阶段发布，几分钟撤销）；**爆炸半径决定门槛**；**回归暴露快**；**不追责**——你修是因为你最了解上下文，事故复盘看的是系统。
-  Ownership 也是共享的：公开频道里任何人都能接线程、指出缺口，反馈可以来自不拥有这块代码的人。

### 8. 方向变了怎么办

- agent 让「开始做」变得很便宜，所以有些工作**不应该合入**。
- 通常是在频道里有人问「为什么做 / 之前不是这么定的 / 有没有更简单的路」，作者自己关掉或改写 PR。
- 因为写得快，关掉 PR 不心疼。关键是**在讨论早期提出不同方向**，而不是在完成的 PR 上留一个阻塞评论。

### 9. 怎么在自己团队落地（清单）

**PR 之前**

- 给 agent 可运行的检查，写进简短的 `CLAUDE.md`；加 hooks 跑 formatter / linter。
- 本地跑 `/code-review`、`/security-review`，或让 fresh-context subagent 审。
- 加 `REVIEW.md`，把重复的评审意见搬进去。

**每个 PR**

- 强制 CI；PR 模板加「Testing / Risk / How to revert」。
- 先在一个仓库接 AI reviewer，调几周 `REVIEW.md` 再推广。
- 加自动安全评审；合并前要求**所有 review thread 已解决**。
- 评审力度匹配风险（Quick / Standard / Deep）。
- **限制评审轮数**；前几轮之后只审新 diff。

**批准**

- 写下风险等级，**按变更定级而非按作者**；先严后松，用证据放宽。
- 轻量路径只给受信任作者。
- 用 CODEOWNERS + 分支保护，让 auth、计费、CI、发布 workflow、安装器**永远需要人**。
- **绝不让 bot 的批准替代必需的人类批准**；新 commit 到来时撤销旧批准。

**合并与之后**

- merge queue、feature flag、内部先用、分阶段发布、一步回滚。
- 把事故与 revert 变成 eval 集；reviewer 的 prompt / 工具 / 模型一变就重跑。
- 度量人的时间，用 revert / incident 率当护栏。

### 10. 我的 takeaway

- **评审的本质不是「读代码」，而是「风险分配」**：把每种风险交给最合适的检查层。
- **自动化不等于取消人**：低风险零人工，高风险反而加人；「谁提出变更谁负责」这条没有变。
- **agent 时代的新问题是收敛**：作者和评审都是 agent 时，会互相刷轮次；必须设**轮数上限、只审新 diff、按类别修**。
- **护栏比指标重要**：省时间不能靠把成本推到事故侧；revert / incident 率是判断「真省了还是转移了」的关键。
