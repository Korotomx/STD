当 90% 的代码由 Claude 写时，Claude Code 团队没有取消评审，而是把大部分阅读交给机器：评审从“PR 末尾的人工关卡”变成“写代码时全程运行的拼写检查”，人的时间只花在只有人能判断的事上，同时用 revert / incident 率当护栏，确保省下的时间没有变成事后救火。

> 来源：Anthropic 官方博客《How the Claude Code team does code review》

## 背景

- Claude 写了 Claude Code 自身约 **90%** 的代码。
- 6→9 月，合并的 PR 数翻倍多，被回滚的 PR 占比下降 40%+。
- 单体仓库每天落地的变更从 5 月约 **2,500** 涨到 9 月 **30,000+**。

## 评审的目的与度量

评审有两个职责：发布前发现问题；在团队内建立共享上下文。“有人读过代码吗”是不精确的代理指标，更好的问法是：这次变更可能出什么问题，该由哪种检查来抓。评审因此从“写完 → 开 PR → 等同事”的末端关卡变成持续过程；多数变更在人类看到前已被 Claude 评审并修过至少一轮。

人的成本有两头：评审花的时间 + 坏代码出事后修复的时间。只砍第一头，时间会从第二头冒出来。目标：大多数 PR 最多一个人类 in the loop，且 revert / incident 率不上升。度量人类批准数（中位数 + P95）、评论数、PR 等人时长；revert / incident 率是判断时间“真省了还是转移了”的护栏。

## 七层流程

| 层 | 做什么 | 谁 |
| --- | --- | --- |
| 1. PR 之前 | 跑测试/构建/截图对比；fresh context 的 subagent 审 diff；skills 找 bug、简化、端到端检查 | Claude + 作者 |
| 2. 每个 PR | AI 评审对照整个仓库和 PR 意图，判断是否解决问题、契合系统、弄坏别处 | Claude |
| 3. 安全评审 | 独立检查；任一未关闭发现都阻塞合并 | 自动 |
| 4. CI | lint、类型、全平台测试、构建；PR 模板填怎么测、风险、怎么回滚 | CI |
| 5. 人工批准 | 按风险等级决定 0 / 1 / 2 人 | 人 |
| 6. 合并 | merge queue 在最新 main 重跑检查；feature flag + 内部先用 + 分渠道发布 | 自动 |
| 7. 合并后 | 快速发现、快速回滚；on-call；事故复盘问“哪一层本该拦住” | 人 + 监控 |

**第 1 层**：给 Claude 可运行的东西（测试、构建、设计稿截图），要求它展示输出，而不是口头说“做完了”；再让 fresh context 的 subagent 审 diff。给 Claude 一个验证自己工作的方式，能让最终质量提升 2~3 倍。同一类问题反复出现时从源头修：改 skill、加 lint 规则、更新 `CLAUDE.md` / `REVIEW.md`。前者写技术栈、约定、目标与非目标；后者由 code owner 写“什么最重要”、失败长什么样、哪些路径可跳过，并要求给出文件和行号作为证据。

**第 2 层**：评审读 diff、整个仓库和 PR 意图，修 bug 时重点找根因。研究预览上线后，内部 PR 获得实质性评审意见的比例从 **16% → 54%**；大 PR 大多能发现问题，小 PR 大多干净返回。每个仓库可选 Quick / Standard / Deep，“漏一个 bug 的代价 > 多花评审时间”的地方才用 Deep。发现先由其他 agent 验证：多个 agent 并行找 bug，另一组投票，票数够才发布；纯风格、诊断、清理类直接丢弃。剩下的按严重程度排序，标注 Important / Nit / Pre-existing——不是本 PR 引入的 bug 不应看起来像作者的锅。每条发现都必须回应：修掉，或写理由 resolve。

**第 3~4 层**：安全发现同样阻塞合并，修掉或写短理由关闭，后续 commit 修好后自动清除。CI 跑 lint、类型、全平台测试、构建，典型 CLI PR 可能跑几十项检查。PR 模板要求回答怎么测、风险是什么、怎么撤销；Claude 可以代填，但提出变更的人要签字确认。

**第 5 层**：

| 风险 | 例子 | 人类批准 |
| --- | --- | --- |
| 低 | 文档、文案、内部功能、flag 后的增量变更 | 自动评审 + 安全全绿后不需要 |
| 中 | 普通产品变更；缓存、自动更新器、system prompt 等敏感区 | 1 人 |
| 高 | 最高风险代码 + 永远需要两人的路径 | 2 人 |

等级由变更决定，不由作者决定：分类器读变更定级，第二个分类器判断“即使等级说不用，这次是否仍需一个人”。owner 标记的敏感路径、任何 CI workflow 文件永远需要人。只有受信任作者能走轻量路径，其他人需要第二人批准；agent 的批准永远不能顶替人的名额。提出变更的人对结果负责；批准只对某个 commit 有效，新 commit 必须重新批准。

**第 6~7 层**：merge queue 在最新 main 上重跑检查，防止两个单独能过的 PR 合起来弄坏 main。新行为先藏在 feature flag 后给内部员工用，公开版本先发 `latest` 再发 `stable`。漏网之鱼靠快速发现和回滚兜底：flag 不用部署就能关，团队每周 on-call，事故复盘问“哪一层本该拦住”。目前还缺“指标一动就自动收紧审批”的 circuit breaker。有同事说，放慢确实能降低错误率，但主要是因为你做得更少；团队宁愿把发现和修复变快。

## 让评审越用越好的闭环

- **事故变成 eval**：收集导致事故的 PR（连同 fix-forward / revert），让熟悉代码的工程师确认 bug 与位置；reviewer 每天跑这套 eval，改 prompt / 工具 / 模型后重新打分。
- **用人的行为度量噪声**：按作者反应分类（修了 / 说它错了 / 有意为之 / 不重要），再拿已知干净的 PR 统计误报率。先抓真 bug，再减评审轮数。噪声对 agent 作者更贵：人能一秒无视 nit，agent 会去修，多一个 commit、多一轮评审。
- **评审必须收敛**：agent 作者 + agent 评审会无限互相忙碌，有一个 CLI PR 一夜跑了 50+ 轮。对反复指出的内容做 `git blame`，约 59% 是 reviewer 第一轮就存在的旧代码——它每轮多翻出几个旧 bug。措施：3 轮后要求作者重新考虑方案；之后只审新 diff；按 bug 类别标记，一次修掉同类；不重复已发过的发现。
- reviewer 每晚跑存量代码，提前抓旧 bug。

## 人还在哪些环节

把资深工程师从深度工作中拽出来抓例行错误，成本远高于自动评审。人负责：

- **决定要不要做**：方向、品味、范围。
- **审高风险代码与架构**：计费、自动更新器、CI workflow、会被人模仿的模式。
- **读证据**：测试输出、命令与返回、截图、reviewer 的发现。说不清这些检查会漏什么，就该要真正的评审，而不是快速 approve。
- **对结果负责**：每个发布出去的变更都有人 accountable。

机器读代码后，团队靠“让 Claude 针对代码切片写讲解”建立共享理解，比逐行读琐碎 diff 更值；默认在公开 Slack 频道工作。

## “你合入，你负责”

小 / 中变更出问题，默认由合入者修。机制是：变更小；一切可逆（flag、revert、分阶段发布）；爆炸半径决定门槛；回归暴露快；不追责——复盘看的是系统。Ownership 共享：公开频道里任何人都能指出缺口。

agent 让“开始做”变便宜，所以有些工作不该合入。通常在频道里有人问“为什么做 / 有没有更简单的路”，作者自己关掉或改写 PR。关键是早讨论方向，而不是在完成的 PR 上留阻塞评论。

## 落地顺序

先在单仓库接 AI reviewer，用 `CLAUDE.md` / `REVIEW.md` 和 hooks 把可运行检查固化，调几周再推广；合并前要求所有 review thread 解决，限制轮数、之后只审新 diff；最后按变更风险放开人工批准，并用 revert / incident 率当护栏，把事故变成 eval 持续回归。

## 结论

- 评审的本质不是读代码，而是**风险分配**：把每种风险交给最合适的检查层。自动化不等于取消人：低风险零人工，高风险反而加人；“谁提出变更谁负责”没有变。
- agent 时代的新问题是**收敛**：作者和评审都是 agent 时会互相刷轮次，必须设轮数上限、只审新 diff、按类别修。
- **护栏比指标重要**：省时间不能靠把成本推到事故侧；revert / incident 率是判断“真省了还是转移了”的关键。
